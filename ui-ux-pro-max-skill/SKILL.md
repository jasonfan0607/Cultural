# Cultural：从需求表达到可验收规格

这是根据 Cultural 项目实际开发过程编写的项目技能，不是对同名第三方技能包的恢复。核心产出是让开发者、测试者和使用者对“完成了什么”有一致判断。

## 使用方式

用户只要求分析时，交付规格和评测方案；用户要求修复或开发时，形成与任务规模相称的规格后继续实现，不把写文档当作完成开发，也不额外插入确认关卡。

小修复可以用“意图 + 边界 + 3～5 条验收条件”表达。多状态或跨模块功能使用 [规格模板](assets/development-spec.md)。复杂度由行为和依赖决定，不由文档长度决定。

首次接触本项目时阅读 [项目事实与经验](references/project-lessons.md)。需要实际规格范例时阅读 [AI 设计与收藏案例](references/worked-spec.md)。评估此技能是否有效时使用 [技能评测集](references/skill-evals.md)。

## 1. 把原话转成开发意图

保留用户的原始请求，随后用一句话写清楚：

> 谁在什么场景下，通过什么操作，希望得到什么可观察的结果；结果需要保留到哪里、多久。

从截图提取症状，不从截图直接猜定根因。把内容分为：

- **事实**：能在当前代码、数据或运行结果中找到证据。
- **假设**：为推进工作采用的可逆默认选择，例如先沿用当前页面风格。
- **待明确约束**：会改变业务语义或实现成本的信息，例如本机历史还是跨设备历史。

只有影响结果且无法从上下文推断的问题才需要询问；等待期间继续做不依赖答案的检查。不要把自己的性能指标、配色偏好或新增功能写成用户原始要求。

## 2. 追踪真实行为，再拆需求

沿着“操作入口 → 事件处理 → 状态 → 数据源 → 持久化 → 展示”查证当前实现。

在 Cultural 中尤其检查：

- 导入了 API 模块不等于实际调用；成功提示不等于数据已保存。
- 文本方案、真实生图、个人中心示例卡片可能分别来自不同的数据源。
- `localhost` 与 `127.0.0.1` 的浏览器存储相互隔离；本机刷新恢复不代表账户同步。
- 服务进程启动、HTTP 200、业务成功和数据正确是四种不同证据。

按用户可见行为建立需求 ID，再映射文件或模块。不要直接用“改某文件”代替需求。

| 分解项 | 应表达的内容 |
|---|---|
| 输入 | 来源、必填项、允许值、长度、是否保留原始描述 |
| 状态 | 默认、加载、成功、空、失败；涉及异步时增加取消、重试、过期结果 |
| 输出 | 用户能看到或再次读取的文本、图片、记录、错误信息 |
| 数据约束 | 示例或真实数据、标识、归属、保存范围、过期行为 |
| 交互约束 | 连续点击、切换页面、刷新、键盘输入等与任务相关的路径 |
| 完成边界 | 本次修复包含什么；相邻但未授权的功能只记录，不顺手重做 |

## 3. 把意图写成规格，而不是形容词

每个需求至少有“前置条件、操作、可观察结果、失败条件、验证办法”。

不合格：历史记录可用，图片加载正常，页面美观。

合格：在同一来源地址保存包含文字和图片地址的对话后刷新，点击该记录，应恢复对应消息顺序和封面；若图片地址失效，应显示重试入口；不得用预置空记录替代真实历史。

数值约束注明来源。当前代码里的 500 字、最多 50 条历史、默认 120 秒生图超时是项目现状；修改它们需要本次需求依据。建议的体验指标标为建议，未测量就不能写“已达标”。

## 4. 将规格转换为测试与评测集

建立可追踪链：`用户意图 → REQ → AC → 测试/人工评测 → 证据`。

- **验收条件 AC**：外部可观察的行为，不依赖某个变量名或代码写法。
- **自动化测试**：断言状态、数据和副作用，例如旧请求结果不会写入新对话。
- **人工评测**：判断内容语义、封面与主题是否匹配、布局是否遮挡；保存截图和判断理由。
- **技能评测**：给技能一个新请求，检查它能否正确界定问题并产出可验收规格，不能只检查是否生成了规定标题。

只选与本次任务有关的场景。优先覆盖成功路径和已经发生过的失败；异步任务再检查慢请求、失败、取消及竞态。增加测试应当防止真实回归，而不是复述实现代码。

测试步骤写出环境、输入、操作、预期、判定方法和证据位置。结果只标为“通过 / 失败 / 未执行 / 环境阻塞”；已有脚本不等于本次已通过。

## 5. 用证据定义完成

交付时报告：达成的用户意图、主要改动、验收结果和剩余限制。

必须区分：

- Mock 测试验证错误分支，不能证明第三方服务真实可用。
- 构建通过验证可编译，不能证明页面可用、数据库匹配或图片可加载。
- 图片 `naturalWidth > 0` 可能发生在解码完成前；显示验证还应等待 `decode()` 或 `complete`，再看截图。
- 测试中注入登录标志只用于页面夹具，不证明登录认证或权限隔离有效。
- 本地提交、推送成功和远程提交一致分别验证；只有用户要求提交时才执行发布步骤。

## 6. 将修复沉淀为经验

每次经验条目只写：`触发场景 → 已证实原因 → 有效修复 → 回归证据 → 适用边界`。

例如：收藏封面空白 → 外部随机图且无失败展示 → 对当前示例卡片使用本地主题图并增加失败占位 → 阻断外网仍显示三张图 → 此结论不能替代真实用户收藏的数据接入。

经验应改变下一次的决策，而不是累积“注意质量”等口号。发现旧文档与代码不一致时，以查证后的事实修正经验；保留未实现能力的边界。
