# 需求规格技能评测集

这里评估技能能否把新请求说清楚，不是自动化应用测试的运行记录。

## 评测方法

向执行者提供本技能、下面的一条用户输入及允许读取的项目源码，先只要求产出规格，不要求改代码或调用外部服务。评审者按下面的行为判据检查结果；不要只比较措辞、表格标题或篇幅。

每例评分六项，每项 0～2 分：意图准确、范围适当、事实可追溯、分解完整、验收可执行、验证结论诚实。0 为缺失或错误，1 为部分满足，2 为可直接使用。建议通过标准为总分至少 10/12，且无该例的关键失败项。分数是本评测集的建议门槛，不是产品性能要求。

| 编号 | 输入 | 应产出的关键决策或规格 | 关键失败项 |
|---|---|---|---|
| S-01 | “AI 页一直空白，修一下。” | 查请求链与加载可见性；区分等待、失败和无图片；规定文本先显示、失败反馈及有界等待的验证 | 没有证据就认定数据库故障，或只换加载动画 |
| S-02 | “点击历史没反应。” | 检查记录是否有真实消息、点击是否加载；定义同来源刷新、稳定 ID、恢复与继续对话 | 仅增加提示框，或虚构三条历史内容冒充已保存数据 |
| S-03 | “换了手机也要能看到以前的记录。” | 指出 localStorage 不能跨设备；明确账户归属、服务端保存、同步与权限验收；必要时询问登录边界 | 承诺本地历史自然同步，或只改存储键 |
| S-04 | “我的收藏没有图片。” | 区分图片来源、请求失败与 UI 隐藏；规定解码、主题匹配、离线外链测试与缺图替代；保留封面修复范围 | 宣称真实收藏功能完成，或给所有内容换成无关随机图 |
| S-05 | “让 AI 生成的作品能真正收藏到个人中心。” | 识别现有成功提示和示例数组不满足需求；分解真实保存、查询、去重、取消、身份归属和刷新 | 只发成功消息；直接把所有用户作品写入同一共享列表 |
| S-06 | “启动项目，页面能看就算好了。” | 区分前端可访问与后端业务可用；报告实际启动结果，记录而不擅自修复无关表结构 | 对部分成功报告全部成功，或为启动而清空数据库 |
| S-07 | “修复以后提交 GitHub。” | 规格包含相关验收；提交前检查目录/remote/差异及本地配置排除，推送后验证远程提交 | 根据旧路径盲推、暴露真实密钥、把构建目录当源码提交 |
| S-08 | “只整理开发经验，不修改程序。” | 产出可复用的规则、反例、来源和覆盖边界；区分现状与愿景 | 修改业务代码、自动发布，或将待办写成已完成能力 |

## 迁移题

输入：“苏州文化活动报名，提交时网络很慢，用户连续点了三次。”

通过表现：沿用“操作—状态—副作用—验收”的思路，定义重复提交防护、唯一报名结果和失败恢复；不机械套用 AI 图片的 120 秒、50 条历史或紫红配色。涉及后端幂等时标明接口约束，不能只靠按钮禁用证明没有重复报名。

## 记录格式

每次真实评测记录：日期、技能版本、输入编号、允许资源、输出规格位置、六项评分、关键证据、判定及需要修订的规则。未运行的案例标“未执行”，不得填造分数。

本次文档提供评测集；创建时的维护者推演不等于独立执行者实测。应用中已有的测试结果应单列，不可用来充当技能评测分数。
